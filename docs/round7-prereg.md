# 第 7 轮预注册：放量（`per_source_cap` 1 → 2）

> 原第 7 轮预注册（锚点回滚 `temporal`）**被本轮取代**：那个改动已证明是 no-op
> （时间题在两种 scope 下返回逐字相同，非时间题的 17 片叶子六轮不动），跑它拿不到信息。
> 锚点仍保持 `temporal`（即撤销"锚点全量"），但**本轮的变量是放量**。

## 变更（单一变量）

`retrieval.per_source_cap`: **1 → 2**（config `f3e18d5da770`，2026-10-14 19:56 生效，重启停机 3.0s）。
`time_anchor_scope` 保持 `temporal`、`direct_max_tokens` 保持 `640`。

## 依据（全部是 2026-10-14 新拿到的口径，不是猜测）

1. **平台文档**：Answer 的预算是 **117,760 input token**，且"无静默截断"（`docs/platform-api-notes.md`）。
2. **实测我们只用了它的 1~2%**：官方题 `returned_chars` 中位 9,049（≈2.3k token），
   最长 28,042 字符。**离 117,760 差 50 倍。**
3. **实测大头被 cap 丢掉了**：`rerank_groups` 中位 **52**，`returned` 中位 **16**，
   比值 **0.4** —— 60% 的候选因为"每个 source 只留 1 条"被丢掉。
4. **cap=1 的来历与它失效的原因**：`eval_retrieval.py` 用 **`top_k=10`** 检索
   （`scripts/eval_retrieval.py:241`），在那个口径下"多样性 > 深度"是对的；
   而平台是 **`top_k=100` + 117k token** —— cap=1 是"只有 10 个位置"时代的优化。
   `cap=2` 的遍历顺序仍是按 rerank 分数降序，所以**前 N 条依旧是各 source 的最佳**，
   加深度不会挤掉多样性。

## 预注册判据

| 观察 | 结论 |
|---|---|
| 总分 > 71.27（历史最高）| 放量有效，继续沿这条轴调（cap 3 / `direct_max_tokens`） |
| 总分落在 69~71.3（历史区间内）且 17 片仍不动 | **放量对 A–H 无效**（它们不是被"内容不够"卡住的）→ 换轴（见下） |
| 总分 < 69（低于六轮最低） | 低分内容确实在稀释 → 回滚，并把 cap 固定在 1 |
| 任一低分叶子（D2/G2/G4/H2/F1）第一次变动 | 强信号：那些片是"内容不够"导致的，值得单独深挖 |

**噪声提醒**：平台自身两轮差 ~0.97，C1/C2 本来就在两档间跳（**同配置的 14:27 与 15:28
就不同档**）——所以**只看总分不足以判定**，以实例级（4 条 QA feedback）+ 叶子是否出现**新**变动为准。

## 回归锚点

`locomo1`（"When Jon has lost his job as a banker?"）必须仍是 **1.0** —— 它是小 scope、
有锚点，是唯一有因果链的实例（见 AGENTS.md 的时间锚点 A/B）。本地重放已确认该题
`returned` 从 ~10 涨到 **28** 条且响应 200。

## 回滚方式

`per_source_cap` 改回 `1`，重启（一行配置，`f3e18d5da770` → `4918b04e1ca3`）。
