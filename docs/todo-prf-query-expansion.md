## 一、用户的原方案（原样记录，7 步）

```
输入：原始查询 q，混合检索器 H，重排序器 R，文档库 D
参数：初始召回 N，扩展词数 m，扩展词权重 α

1. 初始召回：C = H(q, topK=N)                    # 混合检索，N 取 50~100
2. 重排序：  C' = R(q, C)                        # 交叉编码器打分
3. 门控筛选：C_rel = { d ∈ C' | score(d) ≥ θ }   # θ 为相关性阈值
             若 |C_rel| < 3，回退到原始查询，不做扩展
4. 扩展词提取：
   a. 对 C_rel 中每条文档分词、去停用词
   b. 统计词频 TF，计算每个候选词 w 的权重：
        weight(w) = TF(w in C_rel) / (1 + DF(w in D))      # 类 TF-IDF
   c. 取权重最高的 m 个词（m 取 5~10），排除已在 q 中的词
5. 构造扩展查询：q' = q ⊕ α · (w_1, w_2, ..., w_m)   # α 取 0.3~0.5
6. 二次检索：C_new = H(q', topK=N)
7. 重排序输出：R(q, C_new) → 最终结果
```

**用户的设计意图（必须保留）**：
- 扩展带来的**新答案不会太多**，**不会顶替那些相似度很高的答案**；
- **`top_k < 30` 的查询关闭该功能**；
- 参数与流程**允许实现方修改**；
- **预期需要至少 10 次不同的实验**才能验证清楚。

## 二、落地时要改的 4 点（我提的，需在实现时确认）

| # | 原设计 | 改法 | 理由 |
|---|---|---|---|
| 1 | `q' = q ⊕ α·(w…)` 文本拼接 | **embedding 向量插值**：`v' = normalize(v_q + α · Σ v_w)` | 文本拼接时 embedding 模型对"α"无感（权重是摆设）；插值才让 α 真正生效。现有 embedding 服务（7999）可一次批量编码 m 个词 |
| 2 | 输出 `R(q, C_new)` | **并集 + 原查询重排**：`C_all = C ∪ C_new`，再 `R(q, C_all)` | 这是"不顶替高相似度答案"的**机制保证**，而不是靠"扩展词少"来期望 |
| 3 | θ 是固定阈值 | **自适应分位数**（C' 分数的 p60 / p75） | 我们的 rerank 分数是 0.04 量级的连续值，绝对阈值跨 scope 不可比 |
| 4 | `DF(w in D)` 遍历库 | **FTS5 直接查** | 已有索引，避免扫库 |

**另外三条实现要求**：
- **漂移哨兵**：记录每题选出的扩展词；若扩展词集合与 query 的语义距离超阈值则自动回退（查询漂移是 PRF 唯一真正的失败模式，必须让它可见，而不是静默生效）。
- **`top_k < 30` 关闭**（用户要求）。
- **回退路径**：任何一步失败（C_rel < 3、扩展词为空、二次检索为空）都必须退回原始结果，**不能返回更少的内容**。

## 四、已知的反面证据（必须正视，但结论不通用）

AGENTS.md 第 18 条：**"规则式多查询扩展更差"** —— 去停用词 / 切前后半后各自检索再合并，
`ids_all` single 92.5% > vote 88.8% > union 86.2%；结论是"规则变体破坏语义、合并又稀释原排序"。

**为什么仍然值得试**：第 18 条测的是**机械切分**（去停用词、切前后半），
而本方案是**从检索结果里学扩展词**（伪相关反馈），信息量完全不同。
**但第 18 条的机制警告成立**：合并会稀释原排序 → 所以第 8 项的"并集 + 原查询重排"是**必须**的。

**另一个需要正视的事实**：`audit_answer_coverage.py` 跑完 41 题的结果是 **MISS = 0**
（没有任何一题"scope 里有相关内容却完全没交出去"）。
这意味着 PRF 的收益**不太可能来自"捞回原本召不到的东西"**，
更可能是"把已召到的答案推得更靠前"——预期要放低，但方向仍然有效。
